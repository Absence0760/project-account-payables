# Backend API surface

Every backend router mounted under `/api`, and what each one does. This is the
full catalogue extracted out of the root `CLAUDE.md` so that file stays small
enough to load into every conversation — read this when you need the detail on
a specific prefix.

Related: `backend/docs/api-reference.md` (request/response shapes),
`.claude/commands/endpoint-inventory.md` (generated route inventory).

## Routers

| `/auth` | Login, logout, profile (JWT + Redis blocklist), MFA enroll/verify/disable, MFA challenge; WebAuthn/passkey MFA (`/auth/mfa/passkey/{register,register/verify}`, `GET/DELETE /auth/mfa/passkey[/{id}]`, `/auth/mfa/passkey/authenticate[/verify]` — passkey is a separate code path, gated by `FEOH_MFA_ENABLED`; authenticate endpoints are challenge-token-gated/public, register/list/delete are JWT). **Changing an existing second factor is a step-up operation**: `POST /auth/mfa/enroll`, `POST /auth/mfa/passkey/register`, `DELETE /auth/mfa/passkey/{id}` and `POST /auth/mfa/disable` take an optional `{password?, code?, assertion?}` body and REQUIRE one of them (account password via the shared `pwd_context`, a code from the currently enrolled authenticator, or a **WebAuthn assertion** from an already-registered passkey — challenge minted by `POST /auth/mfa/step-up/passkey {operation}`) whenever the account already has a live factor — an enabled TOTP secret OR any registered passkey, so removing a factor is gated exactly like adding one; first-time enrollment stays frictionless. The assertion path is what lets a passwordless SSO-only account manage its own factors at all — it is bound to its purpose AND its operation via separate single-use Redis challenge slots (`webauthn:auth_challenge:` for login vs `webauthn:stepup_challenge:<operation>:`), so a step-up assertion can't be replayed as a login, a login assertion can't satisfy a step-up, and a register assertion can't authorize a delete. The supplier portal has NO passkey step-up (`WebAuthnCredential` is control-plane, `VendorUser` is tenant-scoped) — it stays password-or-code. Step-ups are throttled 5/min per ACCOUNT and write a PII-free `auth.mfa.step_up.failure` audit row on failure. Enroll-start also no longer touches the account: the candidate TOTP secret waits in Redis (`mfa:pending_enroll:<user_id>`, `FEOH_MFA_ENROLL_PENDING_TTL_SECONDS`) and `/auth/mfa/enroll/verify` is the only writer of `mfa_secret`/`mfa_enabled`, so an abandoned enrollment can never leave the account single-factor. **Credential guessing is throttled on two axes, not one**: the pre-existing per-IP request limit, plus a per-ACCOUNT *failure* budget (`services/rate_limit.py` → `check_auth_failures` / `record_auth_failure` / `clear_auth_failures`) on `/auth/login` (10 per 15 min) and `/auth/mfa/verify` (5 per 15 min) — because an attacker rotating residential proxies stays under any per-IP cap forever, and at `/mfa/verify` they already hold the password and can mint fresh challenge tokens at will. Failures-only with clear-on-success (a correct credential never accumulates), keyed on the SHA-256 of the *submitted* identifier and checked BEFORE the DB lookup, so an unknown address throttles identically and the 429 can't become the enumeration oracle the equalised-timing 401 exists to prevent. The portal budget is tenant-scoped (`slug + identity`) since a vendor address is unique only within a tenant DB. Bounded rolling window, never a sticky lock; the accepted DoS trade-off is documented, not left to be rediscovered. See `docs/authentication.md` § Per-user enrollment + § Brute-force protection |

| `/invoices` | Invoice CRUD, bulk ops, upload, extraction, approve/reject, assignable-reviewer list (`GET /invoices/assignable-reviewers` — admin/ap_manager, matching what `POST /invoices/{id}/assign` gates on; returns `{id, full_name, is_active}` for active org users whose effective permissions include `invoice.approve`, so custom roles work and clerks are excluded. Re-point a payee the same way you re-price: reject → correct → re-approve; `POST {id}/file` attaches a source file afterward, attach-only (409 once the invoice already has one), audited `invoice.file_attached`; `PUT {id}/file` replaces / `DELETE {id}/file` removes an invoice's file (same admin/ap_manager/cfo gate, 404 if none to replace/delete, 409 once the invoice is `done`), audited `invoice.file_replaced`/`invoice.file_deleted` — audit-log summary (`GET/POST {id}/summary`), e-invoice export (`GET {id}/einvoice?format=ubl|cii|fatturapa|cfdi|nfe|dian`, role-gated, 422 on tax-invalid; `ubl`/`cii` are built-in dialects, the rest national formats), PEPPOL AS4 transmission (`POST {id}/peppol-send`, role-gated, idempotent), contract link (`POST {id}/link-contract` \| `/unlink-contract`, spend attribution), inter-company routing (`POST {id}/route-intercompany`, admin/ap_manager — generates the mirror payable under the counterparty entity; idempotent in three layers — the origin is taken `FOR UPDATE`, the service short-circuits on `intercompany_mirror_id`, and the partial unique index `uq_invoice_intercompany_mirror` (migration 0075) makes a duplicate mirror impossible to persist (→ clean 409); the counterparty is only stamped while unrouted; audited on both rows; see `backend/docs/inter-company.md`), supplier chat (`GET/POST {id}/chat`, `POST {id}/chat/attachments`, `POST {id}/chat/{resolve,reopen}` role-gated, `GET chat/templates`, `GET chat/file/{key}` cross-tenant-checked), **email approval** (`GET /invoices/email-action/{token}` confirm page + `POST .../confirm` — PUBLIC, signed single-action token IS the credential; approve/reject the assigned invoice from the notification email with no login, via the normal review path; `email_actions.py` / `services/email_action_token.py`; see `backend/docs/email-approval.md`) |
| `/vendors` | Vendor CRUD, ERP sync; status-chip tallies (`GET /counts` — whole-set, search-aware, so the Unverified attention badge doesn't undercount past page 1); sanctions screening (`POST {id}/screen`, `GET {id}/screening-history`, `GET screening/review-queue`, `POST {id}/block`\|`/unblock` — screen also runs on create/update), vendor risk (`GET {id}/risk`, `POST {id}/risk/recompute`, `GET risk/summary`). | `/vendor-statements` | Vendor statement reconciliation — reconcile a supplier's statement of open items against our AP ledger. `POST` (manual lines) / `POST /upload` (**CSV or PDF**) create a run + classified `VendorStatementReconLine`s (matched / amount_mismatch / missing_on_our_side / missing_on_their_side) via the pure `services/vendor_statement_recon.py`; `GET` list, `GET /summary` (whole-set `by_status` counts + total open discrepancies, sharing the list's `_recon_list_filters`), `GET {id}` detail+lines, `GET {id}/file` (the archived source document — entity-scoped + org-prefix-checked, opaque 404), `POST {id}/lines/{line_id}/resolve` (resolve/ignore), `DELETE {id}` (also deletes the stored object), `GET close-readiness` (period-close gate — vendors with a material unreconciled balance). **A PDF statement goes through the org's own extraction adapter**, not a second parser: `extract_statement` is an OPTIONAL adapter capability in the same shape as `PaymentAdapter.get_balance`/`fetch_settlement` (base reports unavailable; `mock` is a credential-free offline text-layer reader, `claude_vision`/`ollama` share a prompt) — the invoice `extract` path was deliberately NOT reused, because `ExtractedLineItem` has nowhere for the per-row invoice number and date that reconciliation matches on. | `/payments` | Payment listing, payment runs (create/execute). Run creation refuses any invoice carrying an unresolved (`open`/`escalated`) exception in `PAYMENT_BLOCKING_EXCEPTION_TYPES` — `duplicate`, `fraud_flag`, `line_total_mismatch`, `payment_reconciliation` — since approval gates on none of them; resolving/dismissing it is the human sign-off. `payment_reconciliation` is opened by the backstop reconciler when it ages a still-`submitted` payment out to `failed`: that frees the invoice's live-payment slot while real money may still be in flight at the rail, so the invoice is blocked from a new run until a human reconciles. **A run's status is derived from its own payments** (`services/payment_runs.derive_run_status`) rather than read from the column — claim states (`draft`/`executing`/`cancelled`) pass through, outcome states are recomputed — so a run whose held payment was later dismissed can no longer report `submitted` while every button that acts on it 409s (`docs/decisions.md` §41). `GET /payments/summary` and `/payments/queue` report every money total in the org's **reporting currency** (via `currency_conversion.payment_reporting_amount_sql` / `reporting_amount_for_row`) and surface what they could not convert, rather than summing `Payment.amount` — which is invoice-currency — across currencies. `GET /payments/queue` also marks each row `blocked` / `blocked_reason` when that invoice carries an unresolved exception the run-creation gate would refuse — derived from `payment_runs.blocking_exception_types()`, the same predicate `blocked_invoice_ids` uses, so a new blocking type reaches the queue for free; the reason is the exception TYPE only, never its description, because it crosses a JSON boundary to an operator. `POST /payments/corridor-quotes` (admin/ap_manager/cfo, read-only, **advisory**) prices one payable invoice across every configured processor via `services/corridor_quotes.compare_quotes` without booking anything or changing which rail pays it (`docs/decisions.md` §42). A payment held `pending_compliance` by the sanctions/KYC gate now opens a `payment_compliance_hold` Exception (dedup'd per invoice, visible in the normal queue) instead of sitting invisible, and can be moved forward: `POST {id}/compliance/release` (`payment.execute` — re-runs the SAME compliance-then-adapter path, so a still-genuinely-blocked payment surfaces as still-held, never a bypass) or `POST {id}/compliance/dismiss` (`payment.void` — gives up, flips to `failed` with a required reason). Both 409 outside `pending_compliance` and resolve the open exception on success. **Every `completed` processor webhook is settlement-amount-verified**: a verified HMAC authenticates the sender, not the content, so `services/payment_settlement.verify_settlement` compares the amount the processor says it settled against what AP authorized (one-cent tolerance; two authorized legs so an FX payment reporting either the source-currency debit or the target-currency credit still matches). The verdict rides the same append-only audit row that records the money moving — on every completion, `matched` / `amount_mismatch` / `currency_mismatch` / `unverified` alike, so a rail reporting no amount (Dwolla's bare envelope) is a visible blind spot rather than a silent pass. A divergence opens a payment-blocking `fraud_flag` (the type Positive Pay already raises for an altered cheque — the electronic equivalent, so no taxonomy change) and suppresses the early-pay discount capture, which prices off the figure the rail just contradicted. The settled figure is **persisted** (`payments.settled_amount` / `.settled_currency`, migration 0083) beside the authorized `amount`, so `settlement_coverage` can answer the separate question the ERP sync needs — *may this invoice be marked paid?* — and **hold an under-settled or wrong-currency invoice at `payment_scheduled`** instead of reporting a short-paid invoice as settled in full. Over-settlement and an amount-free rail both stay `covered` (the vendor isn't short; a NULL figure is not evidence), so neither strands. A held invoice has two tested exits: `POST {id}/settlement/accept` (`payment.execute`, reason required — declares the shortfall final, releases to `paid`, refuses 409 when the settlement already covers) or the existing `{id}/void` (back to `approved` to re-pay). A rail whose webhook carries no amount (Dwolla) is re-asked via the optional `PaymentAdapter.fetch_settlement` capability — same shape as `get_balance`, guarded at both call sites (webhook fallback + reconciler backstop) so a fetch failure leaves the verdict `unverified` rather than breaking the money path. **The ERP sync-back's own failures are no longer invisible**: `services/payment_erp_sync` is the PRIMARY path that flips `payment_scheduled → paid` (the inbound ERP webhook is the other — it runs the same `settlement_coverage` check off the same persisted `Payment.settled_amount` and holds a short-settled invoice with the same `erp_reconciliation` exception rather than reporting it `paid`), is dispatched one-shot (run execute / payment webhook) and is never re-invoked for an already-`completed` payment — so a leg that raised left the money moved and the invoice stranded forever behind a log line. Each leg now commits independently (a DB error in one used to poison the shared transaction, so the final commit rolled back the run's *successful* transitions too) and every failed leg opens a de-duped, PII-free `erp_reconciliation` Exception naming the payment, the run and the exit.
