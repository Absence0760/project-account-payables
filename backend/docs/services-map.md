# Key services map

What each notable module under `backend/app/services/` is responsible for.
Extracted from the root `CLAUDE.md` so that file stays small enough to load into
every conversation.

Adapter subdirectories (`*_adapters/`) are documented separately in
`backend/CLAUDE.md` § Adapter patterns. Background sweeps are in
`backend/docs/background-sweeps.md`.

| Service | What it does |
|---------|-------------|
| `workflow_engine.py` | Invoice state machine with valid transitions, step orchestration |
| `workflow_step_types.py` | Single source of truth for the workflow step-type vocabulary — `CANONICAL_STEP_TYPES` (order load-bearing: it resolves `WorkflowStep.step_number`), `BUILDER_STEP_TYPES` (orchestration-only, never persisted as a step), the legacy aliases, `is_known_step_type` (the definition-save gate) and `canonical_step_index` (refuses a builder or unknown type by name instead of raising a bare `.index()` ValueError). `workflow_engine` and `workflow_builder` re-export it; the `WorkflowStepConfig.type` Literal is drift-guarded by `tests/test_workflow_step_types.py`. See `backend/docs/workflow-design.md` |
| `extraction.py` | Dispatches AI extraction (platform Claude Vision or BYOK provider) |
| `erp.py` | Pushes approved invoices to ERP with retry logic |
| `review.py` | Approve/reject with field corrections |
| `po_matching.py` | 2-way/3-way/4-way invoice-to-PO matching — invoked by `invoice_warnings.refresh_warnings` after every extraction and on every invoice mutation; result persisted on `Invoice.po_match`. The 4-way leg adds a Quality Inspection gate (pass/fail/partial acceptance). `require_inspection` + amount `tolerance_pct` are resolved per-invoice by `matching_rules` |
| `matching_rules.py` | Pure resolver for the effective PO-match rule — `require_inspection` + `tolerance_pct` per-field from `settings.matching.vendor_rules[<vendor_id>]` → `commodity_rules[<gl_account>]` → org default → hardcoded default. Never raises. See `backend/docs/po-matching.md` § Per-vendor / per-commodity rules |
| `qms_sync.py` | QMS inspection sync — pulls `QMSInspectionRecord`s from the configured `qms_adapters` provider into `quality_inspections`, idempotent upsert on `(org, inspection_number)`, PII-free `quality_inspection.synced` audit. `run_qms_sync_loop` background sweep (mirrors `contract_renewal`); `POST /api/inspections/sync` for manual runs |
| `vendor_matching.py` | Fuzzy vendor matching by tax_id / exact name / normalized-name Jaccard. **Entity-scoped**: all three lookups run against the invoice's own `entity_id` ∪ vendors with a NULL one (`_candidate_query` → `tenant.apply_entity_scope(include_shared=True)`), so a multi-entity tenant can't link subsidiary A's invoice to subsidiary B's vendor — which matters because `Invoice.vendor_id` is what the fail-closed credit-memo guard compares. NULL here means *unstamped* (pre-multi-entity / entity-less invoice), not "shared" as it does on `gl_accounts`; it stays matchable because excluding it would silently duplicate the supplier rather than fail loudly. `match_and_link_vendor` derives the entity from the invoice, so an inter-company mirror matches under the counterparty entity for free; single-entity tenants are unchanged. See `backend/docs/vendor-management.md` § Matching is scoped to the invoice's entity |
| `invoice_warnings.py` | Generates warnings and exceptions (duplicates, fraud, etc.). Also owns **line-total reconciliation** — the pure `reconcile_line_totals` checks the summed `InvoiceLineItem.total` against the header money fields (tax-inclusive → `amount`; tax-exclusive → `subtotal` or the derived net), and a divergence raises an `error` `line_total_mismatch` warning + de-duped exception. The header `amount` is **never** recomputed from the lines. See `backend/docs/line-total-reconciliation.md` |
| `payment_erp_sync.py` | Syncs payment status back to ERP |
| `post_commit.py` | Runs best-effort side effects **after** the caller's transaction commits — queue a job on the session, fired from SQLAlchemy's `after_commit`, so no third party's latency is charged to an open transaction holding row locks. `notification_dispatch` and `vendor_notifications` hand it every email + the chat post; the in-app `Notification` rows stay in the caller's transaction. A rolled-back transaction sends nothing. Spawns tasks on the app loop, awaits inline under a `dispatch_engine_scope` (whose loop would abandon a task). See `docs/decisions.md` §46 |
| `payment_methods.py` | Single source of truth for what a `Payment.method` rail means — on **two** axes. **Tax:** which rails the payer files on a 1099-NEC/MISC vs which the card settlement entity files on a 1099-K (`virtual_card` is the only card rail; unknown/`NULL` stays reportable); pure helpers + a SQL predicate consumed by `tax_1099.build_1099_report`. **Geography:** `INTERNATIONAL_PAYMENT_METHODS` / `DOMESTIC_PAYMENT_METHODS` / `is_international_payment_method` — the canonical international-rail set, imported by `payment_corridor.pick_corridor` (is an override real?), `compliance._kyc_required_for` (the default high-risk set) and `api/payments` via `international_payments.is_international_payment` (is an FX rate locked?), so adding a rail means editing one frozenset instead of three literals. `tests/test_payment_methods.py` is the drift guard on both axes — a rail in the `PaymentMethod` enum, any adapter's `supported_methods`, or `CORRIDOR_OVERRIDE_FEES` fails the suite until it is classified card-or-reportable AND international-or-domestic, and a source scan fails if any module under `app/` re-enumerates the international set. See `backend/docs/tax-1099.md` § Card payments are excluded + `backend/docs/international-payments.md` § One international rail set |
| `storage.py` | S3/MinIO file upload/download |
| `audit_summary.py` | One-paragraph LLM/template summary of an invoice's audit timeline; cached on `invoices.meta`, keyed to an audit-log fingerprint. Fail-soft to a deterministic template (local-dev default). See `backend/docs/audit-summary.md`. |
| `audit_log_shipper.py` | Background loop that ships tenant `audit_log` rows to CloudWatch Logs + S3 Object Lock (SOC 2 centralized WORM store) |
| `adaptive_workflows.py` | Deterministic per-vendor/per-approver approval stats + baseline anomaly + advisory suggestion derivation + the **feedback loop** (`compute_outcome_stats` / `outcome_adjusted_threshold` / `compute_effectiveness` — fold the realised auto-approval overturn rate back into the threshold recommendation; honest insufficient-data states) — all pure, no LLM. See `backend/docs/adaptive-workflows.md`. |
| `workflow_experiments.py` | A/B testing of workflow rules — **pure** deterministic A/B assignment (`assign_variant`: stable hash of invoice id + experiment id, ratio-honouring, no clock/randomness) + per-variant metrics + winner call (`compute_experiment_results`: time-to-approval / touchless / exception / rejection, "not enough data yet" state, no LLM). The DB-touching assignment hook is `workflow_experiments_runtime.py` (`maybe_assign_experiment_variant`, called by `workflow_engine.create_workflow_instance`, best-effort, freezes the variant config onto the snapshot + records the assignment + audit row). See `backend/docs/adaptive-workflows.md` § A/B testing. |
| `supplier_chat.py` | Embedded per-invoice supplier chat — lazy thread create, static `CHAT_TEMPLATES`, the org `supplier_chat.enabled` flag read, and the notification (AP managers / @mentions) + direct supplier portal-link email helpers shared by the AP (`api/invoices.py`) and portal (`api/portal.py`) routes. See `backend/docs/supplier-chat.md`. |
| `discount_roi.py` | Pure annualized-return ROI primitive for early-pay discounts (cost-of-forgoing-discount APR; days accelerated = net due − discount deadline). Shared by the optimizer, the auto-capture sweep, and the per-invoice ROI endpoint. See `backend/docs/dynamic-discounting.md`. |
| `discount_offers.py` | `DiscountOffer` tier selection + savings math + lifecycle mutators (accept/decline/capture/expire) + bulk-vendor offer builder. Pure; never commits. |
| `discount_optimizer.py` | Ranks open offers by APR and greedily selects the highest-yield worthwhile ones within a cash budget (capture vs. cash preservation). Pure. |
| `discount_auto_trigger.py` | Background sweep that auto-accepts open offers clearing `FEOH_DISCOUNT_AUTO_CAPTURE_ROI_THRESHOLD`. Mirrors `contract_renewal`; **only flags `offered → accepted`, never moves money** (CFO-gated payment run still funds). |
| `recurring_invoices.py` | Recurring / subscription invoice generation sweep. Mirrors `discount_auto_trigger` / `contract_renewal`; finds `active` `RecurringInvoiceTemplate`s whose `next_run_on` has arrived, generates the next pre-coded `Invoice` into the approval queue (period_key `YYYY-MM` / `YYYY-Qn` / `YYYY`), advances `next_run_on`, and writes a `recurring_template.generated` audit row. **Idempotent on `(template, period_key)`** via the partial unique index `uq_invoice_recurring_period` — **never moves money** (CFO-gated payment run still funds). Disabled by default (`FEOH_RECURRING_INVOICES_ENABLED`). See `backend/docs/recurring-invoices.md`. |
| `cashflow.py` | Cash-position helpers — the payment-adapter bank-balance auto-sync (`fetch_provider_balance`), the **opening-balance resolution chain + its provenance** (`resolve_opening_balance` → `OpeningBalance{amount, source, currency, provider, account_ref, provider_skipped}`: explicit → provider → persisted `settings.cashflow.opening_balance` → 0), and the persisted per-org alert thresholds / shortfall-alert marker on `Organization.settings.cashflow`. **A provider balance denominated in a currency other than the org's reporting currency is refused** (flagged `provider_skipped="currency_mismatch"`) — the outflows subtracted from it are in the reporting currency, so seeding the curve from a foreign account makes the running balance a silent two-currency mixture; converting is rejected because an FX rate fetched on a read makes the curve non-deterministic. One owner, and all three consumers go through it — the copilot tools, the shortfall sweep, and `GET /api/analytics/cash_position` (whose explicit-override source value is consequently `"explicit"`, not the old `"query"`) — so a copilot answer, an alert email and the `/cfo` chart can't start from different numbers. See `docs/cash-flow-copilot.md` §12. |
| `cash_flow_alerts.py` | **Projected-cash-shortfall alert sweep.** Mirrors `contract_renewal` / `discount_auto_trigger`; per org, skips unless a `settings.cashflow.min_balance_threshold` is persisted (the threshold IS the opt-in), builds the org-wide commitment rows (`entity_id=None` — a treasury shortfall is a whole-group question), resolves the opening balance via `cashflow.resolve_opening_balance`, runs the pure `compute_cash_position` → `detect_threshold_breaches`, and notifies the finance leaders once per projected shortfall period (`cash_shortfall_projected`, `entity_type="cash_position"`). **Never moves money** — its only write beyond the notification rows is the alerted-period marker on the org's settings JSON (the dedupe; cleared when the projection clears so a recurrence re-alerts). Audience `ALERT_ROLES` is drift-guarded against `api/cash_flow.py::COPILOT_ROLES`. Disabled by default (`FEOH_CASHFLOW_SHORTFALL_ALERTS_ENABLED`). See `docs/cash-flow-copilot.md` § Proactive projected-shortfall alerts. |
