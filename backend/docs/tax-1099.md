# 1099 tracking & reporting (US tax compliance)

US AP teams need to file IRS 1099-NEC (contractor payments) and/or
1099-MISC forms for any vendor they pay ≥ $600 in a calendar year. This
doc covers what's shipped, what the tenant has to do manually, and how
to add real e-filing when a customer needs it.

## What's shipped

### Data model

Five columns added to ``vendors`` (migration `0011_vendor_1099_fields`):

| Column | Purpose |
|---|---|
| `tax_classification` | IRS entity type from W-9 box 3 (`individual`, `sole_proprietor`, `llc_s_corp`, `llc_c_corp`, `llc_partnership`, `c_corp`, `s_corp`, `partnership`, `trust`, `other`). |
| `is_1099_eligible` | Flag set by AP when collecting W-9. C-corps / S-corps are **not** 1099-eligible for services; we don't auto-derive because corporate exceptions (legal, medical) and tenant judgement apply. |
| `w9_received_date` | Date the AP team accepted the W-9. |
| `w9_file_key` | S3 key for the uploaded PDF. Null if not yet received. |
| `tin_verified_at` | Timestamp of the last successful IRS TIN match. Null until the Tax1099 integration lands. |

The existing `tax_id` column (VARCHAR(50)) already holds the TIN /
EIN / SSN from the W-9 box 1–2.

A second tenant-scoped table, `tax_1099_filings` (migration
`0026_us_tax_1099`), records every 1099 e-filing batch — one row per
submission, keyed for idempotency on `(organization_id,
idempotency_key)`. It carries **no recipient TIN**: only counts, the
confirmation number, and a redacted per-form result list. See
[E-filing](#e-filing) below.

### API

All endpoints are `admin` + `ap_manager`. The read-only ones (report,
dashboard, form download) also allow `cfo`; TIN validation and e-filing
do not (they mutate compliance state):

| Endpoint | What it does |
|---|---|
| `GET /api/tax/1099-report?year=YYYY` | Per-vendor aggregate of completed **non-card** payments in the calendar year, flagged if ≥ $600 and if a W-9 is on file. Card-rail spend is excluded from the reportable total and surfaced separately — see [Card payments are excluded](#card-payments-are-excluded-1099-k-not-1099-necmisc). |
| `GET /api/tax/1099-dashboard?year=YYYY` | Compliance-readiness view: every 1099-eligible vendor with YTD totals, W-9-on-file + TIN-verified + threshold flags, and a `needs_attention` flag (over threshold, missing W-9 or unverified TIN). The filing-season chase list. |
| `POST /api/tax/vendors/{id}/tin-verify` | Validate the vendor's TIN through the configured TIN-validation adapter. On a `valid` verdict, stamps `tin_verified_at`; on `invalid`/`unknown`, clears it. Body may pass `{"tax_id": "..."}` to update + validate a new TIN in one call. Response carries the verdict + redacted last-4 only — never the TIN. |
| `GET /api/tax/vendors/{id}/1099?year=YYYY&form_type=1099-NEC` | Generate + download the vendor's 1099-NEC / 1099-MISC working-copy PDF. The form prints the vendor's boxes **for that form** (see [Per-box allocation](#per-box-allocation)) with a total beneath them — not the whole reportable total. 400 if the vendor has no reportable payments for the year, or none that land on the requested form. `misc_box=N` now only selects the box for a caller-built row that carries no allocation. |
| `POST /api/tax/1099/file` | Submit a year's 1099s for e-filing via the configured adapter. Body: `{"year": YYYY, "form_type": "1099-NEC", "idempotency_key": "..."}`. Idempotent on `(org, idempotency_key)` — a retry returns the stored confirmation (`already_filed: true`) instead of re-filing. Only 1099-eligible vendors over the $600 threshold are filed, and each is filed for **its own subtotal on that form** — a vendor with rent and contractor spend is filed once per form, never once for the combined figure. The response + the stored row carry a `box_breakdown`. |
| `POST /api/tax/vendors/{id}/w9` | Upload the signed W-9 PDF, set `w9_received_date`, flip `is_1099_eligible`. |
| `PATCH /api/tax/vendors/{id}/w9` | Update tax fields without re-uploading (e.g. marking a vendor 1099-ineligible after a legal review). |

### Reporting currency (enforced, not asserted)

`currency` is the org's **reporting (home) currency** (resolved via
`currency_conversion.resolve_reporting_currency` — `settings.reporting_currency`
→ `payments.home_currency` → `invoice_defaults.currency` →
`FEOH_REPORTING_CURRENCY_DEFAULT`, default `USD`). It is the currency
`total_reportable` and every per-vendor `ytd_paid` are denominated in.

**`Payment.amount` is denominated in the INVOICE's currency, not the org's
home currency.** `international_payments.prepare_international_payment` sets
`amount=invoice.amount` ("paid in invoice currency") and puts the
home-currency debit on `source_amount` / `source_currency`. Summing raw
`Payment.amount` therefore added a EUR 1,000.00 payment into a USD box amount
at face value — a wrong number on a filed form, and one that can carry a
vendor over (or under) the $600 threshold.

`currency_conversion.payment_reporting_amount_sql` resolves each payment into
`currency`, most authoritative rung first:

1. `Payment.source_amount` when `source_currency` IS the reporting currency —
   the exact home-currency cash outflow, at the rate locked onto the row when
   the payment was submitted.
2. `Payment.amount` when the invoice's own currency IS the reporting currency.
   This is the only rung a single-currency tenant ever reaches, so those
   numbers are unchanged.

A payment neither rung can establish is **left out** of `ytd_paid` /
`card_paid` and counted on `unconverted_payment_count` (per row and in the
summary) — the same "surface the excluded money" posture as
`total_card_excluded`. A non-zero count means the box amount is understated
and the report is not filable as it stands, so an eligible vendor holding one
is flagged `needs_attention` regardless of threshold. Nothing is converted at
read time: a rate fetched on a read would make a filed historical total move
under the reader.

`total_reportable_usd` is retained as a **back-compat alias** of
`total_reportable` (same value); prefer `total_reportable` + `currency`.
`threshold_usd` stays USD-named — the $600 IRS filing threshold is genuinely a
dollar figure. The frontend (`/tax`) reads `currency` from the report as the
authoritative display currency (it no longer guesses from the org store).

Aggregation rules:
- Only `Payment.status == 'completed'` is counted.
- Only payments provably denominated in the reporting currency are summed;
  the rest are counted on `unconverted_payment_count` (above).
- Bucketed by `Payment.completed_at` (year-of-payment, not year-of-
  invoice — this is what the IRS wants). The year comparison is
  **UTC-pinned** (`extract("year", func.timezone("UTC", Payment.completed_at))`),
  not a bare `EXTRACT(YEAR FROM ...)`: `completed_at` is `TIMESTAMPTZ`, and
  Postgres resolves a bare extract against the SESSION's `timezone` GUC before
  pulling the year out — so a payment completed just after midnight UTC on
  January 1st could silently land in the prior filing year on a non-UTC server
  session (or the reverse, near Dec 31). Same pattern
  `bank_reconciliation.py`'s `sent_on_expr` uses. See
  `tests/test_tax_1099_utc_year_cutoff.py`.
- **Card-rail payments are excluded** — see the next section.
- Reversed / voided payments are not netted out. When we add a
  payment-reversal flow, this aggregate needs updating.
- Vendors with zero payments still appear — handy for "which vendors
  do I need to collect W-9s from" triage, even if they're under
  threshold.

### Per-box allocation

A 1099 is not one number in one box. 1099-NEC has a single relevant box (1,
nonemployee compensation); 1099-MISC splits across several, and a vendor whose
spend spans categories — rent AND medical AND legal — is mis-filed if the whole
reportable total is dumped into whichever box the caller happened to ask for.
That was the shipped simplification; it is gone.

**The driver is the money's own coding.** Each completed payment settles an
invoice, and the invoice carries the GL account AP coded it to
(`Invoice.gl_account`). The aggregation groups by `(vendor, gl_account)` in the
same query it already ran, and a per-org mapping turns each GL bucket into a
box.

#### The box catalog

`services/tax_1099.BOX_CATALOG` — the codes a mapping may name, and the only
boxes a form can print:

| Code | Form | Box | Label |
|---|---|---|---|
| `NEC-1` | 1099-NEC | 1 | Nonemployee compensation |
| `MISC-1` | 1099-MISC | 1 | Rents |
| `MISC-2` | 1099-MISC | 2 | Royalties |
| `MISC-3` | 1099-MISC | 3 | Other income |
| `MISC-6` | 1099-MISC | 6 | Medical and health care payments |
| `MISC-10` | 1099-MISC | 10 | Gross proceeds paid to an attorney |

Deliberately **not** the whole IRS form. Boxes an AP system cannot originate
(federal income tax withheld, fishing-boat proceeds, 409A deferrals, FATCA)
have no payment that could land in them, and offering a box nothing can
populate only invites a mapping rule that routes real money into a box the
filing partner will reject.

#### The mapping (per-org JSON, no migration)

`Organization.settings.tax.boxes` — the same place every other per-org tax
setting lives:

```json
{
  "tax": {
    "boxes": {
      "fallback_box": "NEC-1",
      "gl_accounts": {
        "6010": "MISC-1",
        "6400": "MISC-6",
        "71*":  "MISC-10",
        "6000": "NEC-1"
      },
      "vendors": {
        "8f1c…-vendor-uuid": "MISC-10"
      }
    }
  }
}
```

Resolution order for one GL bucket, most specific first:

1. **`vendors[<vendor id>]`** — a per-vendor override that beats every GL rule.
   An attorney's payments are gross proceeds however the invoice was coded.
   (It lives in the org settings blob rather than on the `Vendor` row: there is
   no general-purpose vendor JSON column, and borrowing `bank_details` /
   `risk_factors` / `beneficial_owner_data` — each owned by another feature —
   to carry a tax setting is how columns rot. No migration either way.)
2. **`gl_accounts["<exact code>"]`** — case-insensitive, whitespace-trimmed.
3. **`gl_accounts["<prefix>*"]`** — a prefix rule over the chart's hierarchy.
   Longest prefix wins; an exact code always beats a prefix.
4. **`fallback_box`** — see below.

**Platform default: no mapping at all.** With no `settings.tax.boxes`, every
rule set is empty, the fallback is `NEC-1`, and every vendor's whole reportable
total lands in NEC box 1 — *exactly* the pre-allocation behaviour, so nothing
changes for a tenant that hasn't configured anything. What changes is that the
report now says so out loud (below).

**A box code that isn't in the catalog is dropped, never guessed.** A typo in
`fallback_box` falls back to `NEC-1`; a typo in a `gl_accounts` /`vendors`
value drops that rule, so the affected spend takes the fallback path and shows
up as unmapped. The bad codes are logged once per report build (config strings,
never PII) and carried on `BoxMapping.invalid_box_codes`. A malformed settings
blob never raises — the 1099 report must not go down in January because
somebody put a list where an object belongs.

#### The fallback rule

Spend that matches no rule is **not dropped and not quietly folded**. It lands
in the named `fallback_box` — it is filed, in a real box — and the amount is
separately surfaced:

| Field | Where | Meaning |
|---|---|---|
| `unmapped_paid` / `unmapped_payment_count` | per row | this vendor's reportable money that reached the fallback for want of a rule |
| `total_unmapped` | summary | the same across the filed population |
| `fallback: true` | on the box that absorbed it | distinguishes "everything is in box 1" from "nothing was ever mapped" |

The `/tax` console renders all three: a **1099 box allocation** panel under the
KPI row (per-box totals, payment counts, a fallback tag), a per-vendor split
under the YTD Paid figure, and an **Unmapped box** filter chip that narrows the
table to exactly the vendors needing a mapping rule. Guard:
`frontend/tests-e2e/tax/box-allocation.spec.ts`.

Deliberately **not** wired into `needs_attention`: with the default (empty)
mapping every vendor is unmapped, so folding it into the chase list would make
that flag useless for the W-9 / TIN gaps it exists to surface.

#### The reconciliation guarantee

**Every payment lands whole in exactly one box.** Nothing is prorated, split by
percentage, or apportioned across an invoice's line items — so there is no
rounding step, and therefore no residual to shed or invent. The per-box
`Decimal`s sum to the vendor's reportable total to the cent, by construction
rather than by a correction pass:

```
sum(row.box_allocations[*].amount) == row.ytd_paid        # exactly
sum(summary.box_allocations[*].amount) == total_reportable # exactly
```

The residual is published anyway — `box_unallocated` per row and on the
summary, plus `box_allocation_reconciled` — because a guarantee nobody can read
is a guarantee nobody can check. It is `"0.00"` for every row the aggregation
produced. (A row built by hand, carrying no allocation, reports its whole
`ytd_paid` as unallocated rather than pretending to be split.)

Money stays `Decimal` end to end — the aggregation sums `Numeric` in Postgres,
the fold adds `Decimal`s in Python, and every wire field is an exact decimal
string. No float anywhere.

#### Interaction with the card-rail exclusion

The allocation operates on the **reportable population only**. The GL buckets
it sees carry the non-card payments (the same `~is_card` predicate from
`services/payment_methods`, unchanged and not restated), and card spend is
summed apart onto `card_paid` / `total_card_excluded`. So a vendor paid $1,200
rent by ACH and $777 rent by virtual card shows `MISC-1 = 1200.00`, never
`1977.00` — the card leg is the processor's 1099-K, in every box.

#### Forms and filing

`GET /api/tax/vendors/{id}/1099` prints the boxes belonging to the requested
form, each on its own line, with a total row beneath them once there is more
than one. A vendor whose spend is entirely rent has nothing to put on a NEC
form: the endpoint 400s rather than rendering a $0.00 form that looks filable.

`POST /api/tax/1099/file` files each vendor for **its own subtotal on that
form**, and leaves out a vendor with no amount on it. A tenant with both rent
and contractor spend therefore files twice — once per `form_type` — which the
`/tax` filing modal now exposes as a form-type selector with the per-form
vendor count and total.

The transmitted `FilingFormPayload` carries **both** the form total
(`box_amount`) and the split behind it (`box_amounts`, box code → `Decimal`),
because a 1099-MISC with rent *and* medical payments is two boxes on **one**
form — sending only the total files the whole figure in whichever box the
partner defaults to. `box_amounts` is empty when there is no split to send (a
hand-built row, or a tenant with no mapping configured), and a consumer then
files `box_amount` against its own box of record, which is the pre-allocation
behaviour. The `tax1099` adapter transmits it as a `boxes` object of
string-Decimals, omitted entirely when empty. The detail also rides the record
of the filing: `box_breakdown` on the response and on the persisted
`Tax1099Filing.result`, and PII-free box **totals** on the `tax_1099.filed`
audit row. A filing made before this shipped has an empty `box_breakdown` —
stored records are the history of what was transmitted and are never
back-filled.

Guards: `tests/test_tax_1099_boxes.py` (mapping resolution, the reconciliation
guarantee incl. a repeating-cent split, the fallback surfacing, the card
exclusion holding per box, and the form/filing endpoints).

### Card payments are excluded (1099-K, not 1099-NEC/MISC)

The IRS puts payments settled over a **payment card** on Form 1099-K,
filed by the card settlement entity — not on the payer's 1099-NEC /
1099-MISC:

> Payments made with a credit card or payment card and certain other
> types of payments, including third-party network transactions, must be
> reported on Form 1099-K by the payment settlement entity … and are not
> subject to reporting on Form 1099-MISC [or 1099-NEC].
> — IRS, *General Instructions for Certain Information Returns*

So a vendor paid $10,000 by ACH and $5,000 by virtual card gets a
**$10,000** box-1 figure, not $15,000. Filing $15,000 over-reports the
vendor's income and double-counts the card leg against the processor's own
1099-K.

The rail-by-rail classification is `backend/app/services/payment_methods.py`
— the single place this decision lives, so it can't drift out of sync with
the rails the app can actually write:

| `Payment.method` | 1099 treatment | Why |
|---|---|---|
| `ach` | reportable | Bank ACH credit — a direct payment by the payer. |
| `wire` | reportable | Domestic bank wire. |
| `rtp` | reportable | RTP / instant bank rail. |
| `check` | reportable | Paper cheque drawn on the payer's account. |
| `sepa` | reportable | SEPA Credit Transfer — a bank rail. |
| `international_ach` | reportable | NACHA Global ACH / IAT — a bank rail. |
| `international_wire` | reportable | SWIFT wire. |
| `bacs` | reportable | UK BACS — a batched domestic bank credit. |
| `faster_payments` | reportable | UK Faster Payments — instant domestic bank credit. |
| `chaps` | reportable | UK CHAPS — same-day high-value domestic bank credit. |
| `virtual_card` | **excluded** | Payment card; the issuer/network is the settlement entity and files the 1099-K. |
| unknown / `NULL` | reportable | What the manual / legacy payment path writes. Defaulting an unclassified rail *out* would silently drop filed money — under-reporting is as wrong as over-reporting. |

`tests/test_payment_methods.py` is the drift guard: it fails if a rail shows
up in the `PaymentMethod` enum, in any payment adapter's `supported_methods`,
or in the corridor selector's method table (`payment_corridor.
CORRIDOR_OVERRIDE_FEES`) without a treatment above — a new rail cannot ship
with its tax treatment undecided.

**The excluded money is surfaced, not dropped.** Every report / dashboard row
carries `card_paid` + `card_payment_count` alongside `ytd_paid`, and the
summary carries `total_card_excluded` (summed across **all** vendors, not
just the eligible-over-threshold ones `total_reportable` covers — the card
processor's filing knows nothing about our eligibility flags). Use it to
reconcile our 1099 totals against the 1099-K the processor sends the vendor.

The `/tax` console renders all three, deliberately subordinated to the
reportable figure (that is the number that gets filed, so it stays the one you
read first):

- a **Card excluded (1099-K)** column beside YTD Paid — the vendor's `card_paid`
  as money plus a `card_payment_count` sub-line, or `—` when the vendor took no
  card money. Muted styling; the *column header* is what identifies it, so the
  distinction survives without colour.
- a secondary line under the **Total reportable** KPI —
  "Excludes {amount} paid by card — the processor reports that on a 1099-K" —
  rendered only when `total_card_excluded` is non-zero.
- a **Card excluded** filter chip that narrows the table to exactly the vendors
  with a card leg: the reconciliation worklist to tie against the processor's
  1099-K.
- a standing footnote on the report meta line restating why the money is out.

Guards: `frontend/tests-e2e/tax/dashboard.spec.ts` (the `card-payment
exclusion` describe block patches the report response so the rendering is
pinned regardless of seed drift).

**Filings made before this behaviour landed may be inflated.** Nothing is
back-filled: a `tax_1099_filings` row is the historical record of what was
actually transmitted, and rewriting it would falsify the audit trail. If a
prior year was filed while card payments were being counted, re-run
`GET /api/tax/1099-report?year=YYYY` — any vendor with a non-zero `card_paid`
was over-reported by that amount, and the correction goes through the filing
partner as a corrected 1099 (the partner owns corrections; see
[E-filing](#e-filing)).

## What the tenant does each year

Typical January workflow for a US tenant:

1. **Work the dashboard.** `GET /api/tax/1099-dashboard?year=YYYY` and
   chase every `needs_attention` row — these are over-threshold,
   1099-eligible vendors still missing a W-9 or a verified TIN. Upload
   returned W-9s via `POST /api/tax/vendors/{id}/w9`.
2. **Validate TINs.** Run `POST /api/tax/vendors/{id}/tin-verify` on each
   eligible vendor — with the `tax1099` adapter configured this is a real
   IRS TIN-match; with the default `mock` adapter it's a format/checksum
   check. A verified TIN stamps `tin_verified_at`.
3. **Check the box allocation.** The **1099 box allocation** panel on `/tax`
   shows how the reportable total splits across the IRS boxes. Anything sitting
   in the fallback box (the **Unmapped box** chip is the worklist) needs a
   GL-account → box rule in `settings.tax.boxes` before filing — see
   [Per-box allocation](#per-box-allocation). The panel also states whether the
   boxes reconcile to the total reportable.
4. **Confirm 1099-eligibility flags.** Vendors paid > $600 but marked
   `is_1099_eligible=false` (typically because they're a corporation)
   need a human sanity check. Exceptions: legal services, medical
   payments, and certain gross-proceeds rows are 1099-eligible even
   for corporations.
5. **Review the forms.** Download a working-copy PDF per vendor via
   `GET /api/tax/vendors/{id}/1099?year=YYYY`.
6. **E-file** via `POST /api/tax/1099/file` (idempotent), **once per form
   type** — a vendor with both MISC-box and NEC-box spend needs both batches.
   With the
   `tax1099` adapter this transmits to the IRS; with the default `mock`
   adapter it's a deterministic dry run. File by **January 31** — the IRS
   deadline for 1099-NEC to vendor AND copy-A to IRS. 1099-MISC deadline
   varies by box type.

## TIN validation

`POST /api/tax/vendors/{id}/tin-verify` validates a vendor's TIN through
a **pluggable adapter** (`backend/app/services/tin_validation_adapters/`,
same registry pattern as the FX / sanctions adapters):

| Provider | What it does |
|---|---|
| `mock` (default) | Offline, deterministic structural validation — EIN/SSN digit grouping + the IRS never-issued-prefix / invalid-area / invalid-group rules (`format_rules.py`). Runs with no cloud account (local-first). Can flag a *malformed* TIN with certainty but only ever reports `name_match: null` for a well-formed one — it can't reach the IRS. |
| `tax1099` | IRS TIN-match skeleton. Runs the offline check first, then calls the partner's real-time TIN-match endpoint. Without an `api_key` it degrades to format-only (`reason_code: format_only_no_api_key`) — it never fabricates an IRS match it didn't make. Live key required to call out. |

Provider is selected per-org via
`Organization.settings.tax.tin_validation.{provider,api_key,...}`, falling
back to the process-level default `FEOH_TIN_VALIDATION_PROVIDER` (default
`mock`). On a `valid` verdict the endpoint stamps `vendor.tin_verified_at`;
any other verdict clears it so the dashboard never shows a stale green
check against a bad TIN.

**A NAMED provider we have no adapter for is refused, never `mock`.**
`get_tin_validation_adapter` resolves an absent/empty provider to `mock` (the
local-first default — format validation with no cloud account is genuinely
useful) but raises `UnknownTinValidationProviderError` for a name that isn't
registered. It used to fall back to `mock` there too, and `mock` is not an
inert stub: it never reaches the IRS, so it cannot tell whether a well-formed
TIN is actually *assigned* to the named entity — yet `tin_verified_at` was
stamped from its verdict, and that stamp is what the dashboard reads as "TIN
verified" and what B-notice / 24% backup-withholding decisions key off. One
typo in an admin-entered provider name turned an IRS TIN-match into a regex.
The route resolves the adapter **before anything on the vendor row moves** and
turns the refusal into a **409** naming the bad value and the registered
alternatives — `tin_verified_at` and the stored `tax_id` are left exactly as
they were. Same call `decisions.md` §29 made for the payment / ERP / FX
dispatchers and §36 for sanctions. Guard:
`tests/test_adapter_registry_fail_closed.py`.

**PII:** the result object and the HTTP response carry only the verdict +
the redacted last-4 (`tin_last4`) and a machine `reason_code` — never the
raw TIN. The TIN goes out in the partner request body (the API requires
it) but is never logged.

**The `tax1099` connection probe hits `/account/ping`, not `validate`.** It
used to call `validate(tin="00-0000000")`, on the reasoning that a
deliberately malformed TIN would exercise auth without spending a billable
lookup. It did neither: `validate` runs the **offline** `check_format` first
and returns `format_invalid` before any HTTP, so the probe never left the
process and answered `True` for any non-empty `api_key`. A connection test
exists to catch a wrong or expired credential; one that reports healthy on the
mere *presence* of a credential confirms the misconfiguration instead, and the
operator finds out at 1099 season. It now issues the same cheap authenticated
`GET {base}/account/ping` its sibling `tax_filing_adapters/tax1099_adapter`
uses (one provider, one endpoint) and returns `False` on any non-2xx or
transport failure. Sending a *well-formed* fake TIN was rejected as the
alternative — that is a real IRS TIN-match lookup against a made-up taxpayer.
Pinned by `tests/test_tin_validation.py` against an in-process
`httpx.MockTransport` (no network), and the class of mistake is guarded
registry-wide by `tests/test_adapter_contract_integrity.py`.

## 1099 form generation (PDF)

`GET /api/tax/vendors/{id}/1099?year=YYYY&form_type=...` renders the
vendor's 1099-NEC (default) or 1099-MISC working-copy PDF via reportlab
(`services/tax_1099_forms.py`, same pattern as `remittance_pdf.py`). The
box amount is the vendor's reportable YTD total from the 1099 aggregation
(`build_1099_report`, card payments excluded — a vendor paid only by card
therefore has no form to generate and the endpoint 400s), **split across the
boxes that belong on the requested form** — see
[Per-box allocation](#per-box-allocation). Each populated box prints on its own
line with a total row beneath them; `misc_box` now only names the box for a
caller-built row that carries no allocation at all.

This is the payer's / recipient's *working copy* — Copy A (the red-ink
scannable form) must be filed electronically or on official stock, which
is what e-filing below does. TINs are masked (`**-***6789`) on the
rendered form; the full TIN never enters the PDF text layer.

## E-filing

`POST /api/tax/1099/file` submits a year's 1099s through a **pluggable
filing adapter** (`backend/app/services/tax_filing_adapters/`):

| Provider | What it does |
|---|---|
| `mock` (default) | Offline, deterministic, idempotent. Validates each form (well-formed TIN + positive amount + recipient name) and returns an `accepted` / `partial` / `rejected` batch with a confirmation number derived from the idempotency key. Re-submitting the same key returns the same confirmation — the adapter half of the idempotency story. Runs with no cloud account. |
| `tax1099` | Real partner skeleton. POSTs the batch to the partner (which transmits to the IRS FIRE/IRIS + states + recipient copies), passing the idempotency key as the submission reference. Raises if no `api_key` is configured (never a false `accepted`). |

Provider is per-org via `Organization.settings.tax.filing.{provider,api_key}`
falling back to `FEOH_TAX_FILING_PROVIDER` (default `mock`).

**A NAMED provider we have no adapter for is refused, never `mock`.**
`get_tax_filing_adapter` resolves an absent/empty provider to `mock` (the
local-first default) but raises `UnknownTaxFilingProviderError` for a name that
isn't registered. `mock` "accepts" every well-formed batch and returns a
deterministic `MOCK-<year>-<hex>` confirmation, which this endpoint persists on
a `Tax1099Filing` row, records on a `tax_1099.filed` audit row, and answers
200 — so one typo in an admin-entered provider name told the org its 1099s were
e-filed when nothing ever reached the IRS, *and* burned the idempotency slot,
turning the corrected retry into an `already_filed` no-op. The route resolves
the adapter **before the slot is claimed** and turns the refusal into a **409**
naming the bad value and the registered alternatives: no filing row, no
fabricated confirmation, no audit row asserting a transmission, slot still
free. Same call as `decisions.md` §29 / §36. Guard:
`tests/test_adapter_registry_fail_closed.py`.

**Idempotency** (money-/compliance-moving write — a duplicate IRS filing
is a real problem) is enforced at **two layers**:
1. The `tax_1099_filings` row has a unique constraint on `(organization_id,
   idempotency_key)`. The endpoint checks for an existing row first and
   returns the stored confirmation (`already_filed: true`) without calling
   the partner again. Critically, it also **claims the slot before calling
   the partner**: a placeholder row (`status="pending"`) is inserted and
   flushed *before* `adapter.submit_batch` runs, so a concurrent duplicate
   submit hits the unique constraint immediately instead of both requests
   reaching the partner — the loser gets the winner's stored result (or a
   clean 409 in the rare case the winner's own attempt is still failing). If
   the partner call itself fails after the slot is claimed, the placeholder
   row is deleted so a legitimate retry with the same key isn't permanently
   blocked.
2. The adapter is itself idempotent on the same key (deterministic
   confirmation in the mock; submission-reference dedup in the partner).

The key defaults to `"{org}:{year}:{form_type}"` when the caller omits it,
so a naive retry without a key is still safe. Only 1099-eligible vendors
over the $600 threshold are filed.

The persisted `result` JSONB carries only the redacted per-form list
(`vendor_id`, `form_type`, `accepted`, `reason_code`) — **no TIN**.

State filing, corrections (1099-C), and recipient Copy-B mailing are the
partner's responsibility — pick the relevant options in the partner's
submit call; nothing more to build on our side.

## What's NOT shipped (founder roadmap)

### W-9 self-service for vendors

Today: AP collects W-9 via email, uploads PDF to our endpoint.

Future: The supplier portal already exists (see
`backend/docs/supplier-portal.md`). Add a "W-9" tab where vendors can:
- Fill the form in-app (vendor supplies classification + TIN + sign)
- Upload their own signed PDF
- Get notified when it's about to expire (W-9s are valid until vendor
  info changes — no strict expiry)

This is the right long-term answer for scale — stops the AP team from
chasing W-9s manually. Defer until you have >1 customer whose AP lead
is annoyed enough to ask.

### State filing

Several states (California, Oregon, Massachusetts, others) have their
own 1099 filing requirements. Tax1099 handles them when you pick the
"Combined Federal/State Filing" option. Nothing to build on our side;
just set the flag in the Tax1099 submit call.

### International contractor forms

Non-US vendors require W-8BEN / W-8BEN-E instead of W-9. Same data
model works (add "w8_ben" and "w8_ben_e" values to
`tax_classification`), but the reporting form is 1042-S, not 1099.
Scope this when the first customer pays a non-US contractor.

```bash
# Seed creates Acme + TechFlow tenants with sample vendors + payments.
# The two `completed` payments in seed data are stamped 2024-03-25 and
# 2024-03-20, so the report has content only when year=2024.
cd backend && python scripts/seed.py
# Against the Acme tenant API:
curl -H "Authorization: Bearer $TOKEN" \
     -H "X-Tenant-Slug: acme" \
     "http://localhost:8000/api/tax/1099-report?year=2024"
```

The seeded vendors have `is_1099_eligible=false` by default — the
report lists every vendor but `vendor_count_eligible_over_threshold`
will be 0 until a W-9 is attached via
`POST /api/tax/vendors/{id}/w9`. This is correct behaviour for a
fresh tenant.
