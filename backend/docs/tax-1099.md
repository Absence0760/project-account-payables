# 1099 tracking & reporting (US tax compliance)

US AP teams need to file IRS 1099-NEC (contractor payments) and/or
1099-MISC forms for any vendor they pay ≥ $600 in a calendar year. This
doc covers what's shipped, what the tenant has to do manually, and how
to add real e-filing when a customer needs it.

## What's shipped

### Data model

Five columns added to ``vendors`` (migration `0011_vendor_1099_fields`):

| Column | Purpose |
|---|---|
| `tax_classification` | IRS entity type from W-9 box 3 (`individual`, `sole_proprietor`, `llc_s_corp`, `llc_c_corp`, `llc_partnership`, `c_corp`, `s_corp`, `partnership`, `trust`, `other`). |
| `is_1099_eligible` | Flag set by AP when collecting W-9. C-corps / S-corps are **not** 1099-eligible for services; we don't auto-derive because corporate exceptions (legal, medical) and tenant judgement apply. |
| `w9_received_date` | Date the AP team accepted the W-9. |
| `w9_file_key` | S3 key for the uploaded PDF. Null if not yet received. |
| `tin_verified_at` | Timestamp of the last successful IRS TIN match. Null until the Tax1099 integration lands. |

The existing `tax_id` column (VARCHAR(50)) already holds the TIN /
EIN / SSN from the W-9 box 1–2.

A second tenant-scoped table, `tax_1099_filings` (migration
`0026_us_tax_1099`), records every 1099 e-filing batch — one row per
submission, keyed for idempotency on `(organization_id,
idempotency_key)`. It carries **no recipient TIN**: only counts, the
confirmation number, and a redacted per-form result list. See
[E-filing](#e-filing) below.

### API

All endpoints are `admin` + `ap_manager`. The read-only ones (report,
dashboard, form download) also allow `cfo`; TIN validation and e-filing
do not (they mutate compliance state):

| Endpoint | What it does |
|---|---|
| `GET /api/tax/1099-report?year=YYYY` | Per-vendor aggregate of completed payments in the calendar year, flagged if ≥ $600 and if a W-9 is on file. |
| `GET /api/tax/1099-dashboard?year=YYYY` | Compliance-readiness view: every 1099-eligible vendor with YTD totals, W-9-on-file + TIN-verified + threshold flags, and a `needs_attention` flag (over threshold, missing W-9 or unverified TIN). The filing-season chase list. |
| `POST /api/tax/vendors/{id}/tin-verify` | Validate the vendor's TIN through the configured TIN-validation adapter. On a `valid` verdict, stamps `tin_verified_at`; on `invalid`/`unknown`, clears it. Body may pass `{"tax_id": "..."}` to update + validate a new TIN in one call. Response carries the verdict + redacted last-4 only — never the TIN. |
| `GET /api/tax/vendors/{id}/1099?year=YYYY&form_type=1099-NEC` | Generate + download the vendor's 1099-NEC / 1099-MISC working-copy PDF. Amount = the vendor's reportable YTD total. `form_type=1099-MISC&misc_box=N` selects the MISC box (1 rents / 2 royalties / 3 other / 10 attorney). 400 if the vendor has no reportable payments for the year. |
| `POST /api/tax/1099/file` | Submit a year's 1099s for e-filing via the configured adapter. Body: `{"year": YYYY, "form_type": "1099-NEC", "idempotency_key": "..."}`. Idempotent on `(org, idempotency_key)` — a retry returns the stored confirmation (`already_filed: true`) instead of re-filing. Only 1099-eligible vendors over the $600 threshold are filed. |
| `POST /api/tax/vendors/{id}/w9` | Upload the signed W-9 PDF, set `w9_received_date`, flip `is_1099_eligible`. |
| `PATCH /api/tax/vendors/{id}/w9` | Update tax fields without re-uploading (e.g. marking a vendor 1099-ineligible after a legal review). |

### Report structure

```json
{
  "year": 2026,
  "generated_at": "2026-04-23",
  "threshold_usd": "600",
  "vendor_count_total": 42,
  "vendor_count_eligible_over_threshold": 8,
  "vendor_count_over_threshold_without_w9": 2,
  "total_reportable_usd": "87450.00",
  "rows": [
    {
      "vendor_id": "...",
      "vendor_name": "Jane Consultant",
      "tax_id": "123-45-6789",
      "tax_classification": "sole_proprietor",
      "is_1099_eligible": true,
      "w9_received_date": "2026-01-15",
      "w9_on_file": true,
      "ytd_paid": "12000.00",
      "over_threshold": true,
      "payment_count": 12,
      "tin_verified": false
    }
  ]
}
```

The **dashboard** (`GET /api/tax/1099-dashboard?year=YYYY`) is the same
aggregation re-framed around filing readiness. It adds
`vendor_count_eligible`, `vendor_count_over_threshold_tin_unverified`, and
`vendor_count_needs_attention` to the summary, and a per-row
`needs_attention` boolean (eligible + over threshold + missing W-9 or
unverified TIN):

```json
{
  "year": 2026,
  "vendor_count_eligible": 12,
  "vendor_count_eligible_over_threshold": 8,
  "vendor_count_over_threshold_without_w9": 2,
  "vendor_count_over_threshold_tin_unverified": 3,
  "vendor_count_needs_attention": 3,
  "total_reportable_usd": "87450.00",
  "rows": [{ "...": "...", "needs_attention": true }]
}
```

Aggregation rules:
- Only `Payment.status == 'completed'` is counted.
- Bucketed by `Payment.completed_at` (year-of-payment, not year-of-
  invoice — this is what the IRS wants).
- Reversed / voided payments are not netted out. When we add a
  payment-reversal flow, this aggregate needs updating.
- Vendors with zero payments still appear — handy for "which vendors
  do I need to collect W-9s from" triage, even if they're under
  threshold.

## What the tenant does each year

Typical January workflow for a US tenant:

1. **Work the dashboard.** `GET /api/tax/1099-dashboard?year=YYYY` and
   chase every `needs_attention` row — these are over-threshold,
   1099-eligible vendors still missing a W-9 or a verified TIN. Upload
   returned W-9s via `POST /api/tax/vendors/{id}/w9`.
2. **Validate TINs.** Run `POST /api/tax/vendors/{id}/tin-verify` on each
   eligible vendor — with the `tax1099` adapter configured this is a real
   IRS TIN-match; with the default `mock` adapter it's a format/checksum
   check. A verified TIN stamps `tin_verified_at`.
3. **Confirm 1099-eligibility flags.** Vendors paid > $600 but marked
   `is_1099_eligible=false` (typically because they're a corporation)
   need a human sanity check. Exceptions: legal services, medical
   payments, and certain gross-proceeds rows are 1099-eligible even
   for corporations.
4. **Review the forms.** Download a working-copy PDF per vendor via
   `GET /api/tax/vendors/{id}/1099?year=YYYY`.
5. **E-file** via `POST /api/tax/1099/file` (idempotent). With the
   `tax1099` adapter this transmits to the IRS; with the default `mock`
   adapter it's a deterministic dry run. File by **January 31** — the IRS
   deadline for 1099-NEC to vendor AND copy-A to IRS. 1099-MISC deadline
   varies by box type.

### Configuration

| Setting | Default | Purpose |
|---|---|---|
| `AP_TIN_VALIDATION_PROVIDER` | `mock` | Process-level default TIN-validation adapter (`mock` offline \| `tax1099`). |
| `AP_TAX_FILING_PROVIDER` | `mock` | Process-level default 1099 e-filing adapter (`mock` offline \| `tax1099`). |
| `Organization.settings.tax.tin_validation` | — | Per-org override `{provider, api_key, ...}` — wins over the process default. |
| `Organization.settings.tax.filing` | — | Per-org override `{provider, api_key}` — wins over the process default. |

## TIN validation

`POST /api/tax/vendors/{id}/tin-verify` validates a vendor's TIN through
a **pluggable adapter** (`backend/app/services/tin_validation_adapters/`,
same registry pattern as the FX / sanctions adapters):

| Provider | What it does |
|---|---|
| `mock` (default) | Offline, deterministic structural validation — EIN/SSN digit grouping + the IRS never-issued-prefix / invalid-area / invalid-group rules (`format_rules.py`). Runs with no cloud account (local-first). Can flag a *malformed* TIN with certainty but only ever reports `name_match: null` for a well-formed one — it can't reach the IRS. |
| `tax1099` | IRS TIN-match skeleton. Runs the offline check first, then calls the partner's real-time TIN-match endpoint. Without an `api_key` it degrades to format-only (`reason_code: format_only_no_api_key`) — it never fabricates an IRS match it didn't make. Live key required to call out. |

Provider is selected per-org via
`Organization.settings.tax.tin_validation.{provider,api_key,...}`, falling
back to the process-level default `AP_TIN_VALIDATION_PROVIDER` (default
`mock`). On a `valid` verdict the endpoint stamps `vendor.tin_verified_at`;
any other verdict clears it so the dashboard never shows a stale green
check against a bad TIN.

**PII:** the result object and the HTTP response carry only the verdict +
the redacted last-4 (`tin_last4`) and a machine `reason_code` — never the
raw TIN. The TIN goes out in the partner request body (the API requires
it) but is never logged.

## 1099 form generation (PDF)

`GET /api/tax/vendors/{id}/1099?year=YYYY&form_type=...` renders the
vendor's 1099-NEC (default) or 1099-MISC working-copy PDF via reportlab
(`services/tax_1099_forms.py`, same pattern as `remittance_pdf.py`). The
box amount is the vendor's reportable YTD total from the 1099 aggregation
(`build_1099_report`). 1099-NEC puts the total in box 1 (nonemployee
compensation); 1099-MISC puts it in the requested box (`misc_box`, default
3 "other income").

This is the payer's / recipient's *working copy* — Copy A (the red-ink
scannable form) must be filed electronically or on official stock, which
is what e-filing below does. TINs are masked (`**-***6789`) on the
rendered form; the full TIN never enters the PDF text layer.

## E-filing

`POST /api/tax/1099/file` submits a year's 1099s through a **pluggable
filing adapter** (`backend/app/services/tax_filing_adapters/`):

| Provider | What it does |
|---|---|
| `mock` (default) | Offline, deterministic, idempotent. Validates each form (well-formed TIN + positive amount + recipient name) and returns an `accepted` / `partial` / `rejected` batch with a confirmation number derived from the idempotency key. Re-submitting the same key returns the same confirmation — the adapter half of the idempotency story. Runs with no cloud account. |
| `tax1099` | Real partner skeleton. POSTs the batch to the partner (which transmits to the IRS FIRE/IRIS + states + recipient copies), passing the idempotency key as the submission reference. Raises if no `api_key` is configured (never a false `accepted`). |

Provider is per-org via `Organization.settings.tax.filing.{provider,api_key}`
falling back to `AP_TAX_FILING_PROVIDER` (default `mock`).

**Idempotency** (money-/compliance-moving write — a duplicate IRS filing
is a real problem) is enforced at **two layers**:
1. The `tax_1099_filings` row has a unique constraint on `(organization_id,
   idempotency_key)`. The endpoint checks for an existing row first and
   returns the stored confirmation (`already_filed: true`) without calling
   the partner again.
2. The adapter is itself idempotent on the same key (deterministic
   confirmation in the mock; submission-reference dedup in the partner).

The key defaults to `"{org}:{year}:{form_type}"` when the caller omits it,
so a naive retry without a key is still safe. Only 1099-eligible vendors
over the $600 threshold are filed.

The persisted `result` JSONB carries only the redacted per-form list
(`vendor_id`, `form_type`, `accepted`, `reason_code`) — **no TIN**.

State filing, corrections (1099-C), and recipient Copy-B mailing are the
partner's responsibility — pick the relevant options in the partner's
submit call; nothing more to build on our side.

## What's NOT shipped (founder roadmap)

### W-9 self-service for vendors

Today: AP collects W-9 via email, uploads PDF to our endpoint.

Future: The supplier portal already exists (see
`backend/docs/supplier-portal.md`). Add a "W-9" tab where vendors can:
- Fill the form in-app (vendor supplies classification + TIN + sign)
- Upload their own signed PDF
- Get notified when it's about to expire (W-9s are valid until vendor
  info changes — no strict expiry)

This is the right long-term answer for scale — stops the AP team from
chasing W-9s manually. Defer until you have >1 customer whose AP lead
is annoyed enough to ask.

### State filing

Several states (California, Oregon, Massachusetts, others) have their
own 1099 filing requirements. Tax1099 handles them when you pick the
"Combined Federal/State Filing" option. Nothing to build on our side;
just set the flag in the Tax1099 submit call.

### International contractor forms

Non-US vendors require W-8BEN / W-8BEN-E instead of W-9. Same data
model works (add "w8_ben" and "w8_ben_e" values to
`tax_classification`), but the reporting form is 1042-S, not 1099.
Scope this when the first customer pays a non-US contractor.

## Testing

Run the report against the seed data:

```bash
# Seed creates Acme + TechFlow tenants with sample vendors + payments.
# The two `completed` payments in seed data are stamped 2024-03-25 and
# 2024-03-20, so the report has content only when year=2024.
cd backend && python scripts/seed.py
# Against the Acme tenant API:
curl -H "Authorization: Bearer $TOKEN" \
     -H "X-Tenant-Slug: acme" \
     "http://localhost:8000/api/tax/1099-report?year=2024"
```

The seeded vendors have `is_1099_eligible=false` by default — the
report lists every vendor but `vendor_count_eligible_over_threshold`
will be 0 until a W-9 is attached via
`POST /api/tax/vendors/{id}/w9`. This is correct behaviour for a
fresh tenant.
