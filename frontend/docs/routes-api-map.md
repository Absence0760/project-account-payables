# Routes → API mappings

Every SvelteKit route, the backend endpoints it calls, and the role gating on
each. Extracted from `frontend/CLAUDE.md` to keep that file cheap to load.

Read this when wiring a page to the API or when changing a backend route's shape
— it is the fastest way to find every caller. The backend side of the same map
is `backend/docs/api-surface.md`.

| `/` (tenant) | `routes/+page.svelte` | `GET /api/dashboard`. Every reporting-currency figure here can include rows summed at FACE value because no locked rate bridged them, and **each block says so at the grain it is read at** (`decisions.md` §35): the KPI row via one `hasUnconvertedRows` banner (`reporting` + `total_paid` + `total_pending`), and the three charts via their own `role="alert"` notices — the top-vendor tile NAMES the affected vendors (the tile ranks vendors against each other, so which totals aren't comparable is the point), the aging card carries one notice for the five-band set (the API returns one count for it), and the monthly-trend card NAMES the affected months (a trend is read bar against bar). The affected bar and figure are also marked with a stripe + dotted underline — texture, not colour, so the cue survives WCAG 1.4.1 — while the authoritative statement stays in the alert text. The two series rules live in `$lib/utils/dashboardPartials.ts` (`totalUnconverted` / `partialLabels`, unit-tested) rather than inline `reduce`s, for the same reason `discountPartialSet.ts` was extracted. The bare `aging` block deliberately carries no count: it is a face-value cross-currency sum in its entirety, so one would understate it. **The KPI row renders on every state** — `pending={loading}` over `null` values rather than `{:else if data}` — so the most-visited KPI row in the app no longer collapses while its own answer is in flight. The zero-invoice `EmptyState` is the one branch that *replaces* it, and only once the response has LANDED (`isEmptyTenant`), so an empty tenant sees the pending row hand over to it rather than every tenant losing the row on every load (`docs/decisions.md` §125 / §143 / §154). The four conditional cards (exceptions, stale approvals, rebates, captured discounts) stay gated on `data`: they render only when there is something to report, so a pending dash would promise a figure that may never arrive. A failed load leaves the row `unavailable` above the error banner — `tests-e2e/dashboard/error-state.spec.ts`; the pending half is `tests-e2e/a11y/kpi-pending.spec.ts`. |

Two things the UI has to get right here. (a) **The 422 is the normal case, not the edge**: the export refuses to emit a non-compliant document, and the 422 body is now **structured** — FastAPI's own `[{loc, type, msg}]` shape, so the shared `formatApiDetail` flattens it with no endpoint-specific handling, and the client keeps no HAND-WRITTEN code→prose map (the deleted one covered 4 codes and 12 field paths out of dozens, so most rows fell through to a bare rule id). `parseEInvoiceIssues` (in the dependency-free `$lib/api/einvoiceIssues.ts`, so vitest can reach it) splits the flattened join into per-field rows AND recovers the EN 16931 rule id from the `"<CODE>: "` prefix the backend folds into `msg` — the rule id rides on BOTH `type` and `msg` precisely because a client that flattens keeps only `loc` + `msg`, and it is the half a receiving Access Point names. `einvoiceRuleMessageKey` then resolves that code to a **localized** sentence through `$lib/api/einvoiceRuleMessages.generated.ts`, a map GENERATED from the backend's own rule set (`pnpm gen:einvoice-messages`; CI's Backend lint job runs `--check`, `pnpm check` rejects a key `en.ts` lacks because the map is `satisfies Record<string, MessageKey>`, and the locale-parity test then demands the other five). A code this build predates degrades to the raw sentence, never a blank row; the four generic kinds (`missing` / `malformed` / …) are deliberately unmapped — the 422 does not fold those into `msg`, so no client can identify them. Both the e-invoice and PEPPOL failures render through the shared `EInvoiceIssueList.svelte` in a persistent `role="alert"` region (`[data-testid="einvoice-error"]` / `[data-testid="peppol-error"]`), never a toast that fades before it can be acted on; an unparseable detail renders verbatim rather than being reshaped. (b) **PEPPOL is idempotent but still a real outbound**, so it is confirm-then-act (an inline form collecting the receiver scheme + id, mirroring the reject form), and the outcome is read off the RESPONSE: `already_sent: true` renders "Already transmitted", because a second "Transmitted" would claim a document reached the network when the server short-circuited. `GET /api/invoices/{id}/peppol-transmissions` (all four roles, tenant- and entity-scoped, PII-free — participant *values* omitted, schemes only) supplies the state on open, rendered as four distinct states: loading, transmitted-on-{date}, only-failed-attempts (re-sendable), and none. A failed read renders **unknown**, never degraded into "not sent" — the claim the app must not make without evidence. `tests-e2e/invoices/einvoice-export.spec.ts` |

Root layout (`+layout.svelte`) routing logic:
- No tenant subdomain → Landing component (public) or `<slot />` for `/signup` / `/verify`
- Tenant present, not logged in → redirect to `/login` (or `/login/mfa` if a challenge is pending in `sessionStorage`)
- Tenant present, logged in, `must_change_password=true` → redirect to `/change-password`
- Tenant present, logged in, flag clear → app shell with sidebar

MFA flow:
- `/login` calls `auth.login()`. If it returns `{kind:'mfa', challenge}`, the page stashes the challenge in `sessionStorage` and navigates to `/login/mfa`.
- `/login/mfa` reads the challenge, lets the user pick TOTP or email, calls `auth.completeMfa(...)` or `auth.requestEmailMfa(...)`. On success, removes the challenge and navigates home — or to `/profile` if `must_enroll=true`.
- `/profile` renders enrollment (QR + verify) and disable forms backed by `/api/auth/mfa/{enroll,enroll/verify,disable}`.
